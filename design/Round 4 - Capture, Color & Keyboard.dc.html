Round 4 · capture, colour, keyboard

Point the camera at the order

Three additions. Scan-to-fill, because a sender's order details already exist on a screenshot, a label or a handwritten note and retyping them is the slowest part of the flow. A semantic colour set, so status has one definition rather than a hex per surface. And a keyboard-first regular-width layout, which is the iPad design and — as you said — the Mac app for free.

6a scan-to-fill · 6b semantic colour · 6c keyboard & regular width · 6d Dynamic Type without overrides.

6a

Scan-to-fill — one pass, many fields

The design principle that makes this safe: recognition proposes, the sender confirms, and confirmation is per field, not per scan. Anything recognised arrives as a filled row marked as a proposal — tap to accept, edit inline, or dismiss. Nothing is silently trusted, because a misread digit in a phone number is a failed delivery and a misread flat number is a courier at the wrong door.

Three ways in, one result screen: live camera, an image from the library, or a screenshot shared into the app (which reuses the share extension from 5d). Confidence is shown, not hidden — a low-confidence field is visibly a guess.

6b

Semantic colour — status has one definition

Named by meaning, never by hue, so «зелёный» never appears in a diff. Each entry is one asset-catalog colour with light and dark values, generated as a compile-time symbol — a typo becomes a build error rather than a black rectangle in a widget. Every status pairs a colour with a glyph and words, so removing colour costs nothing.

Two rules that keep this honest

A status colour never appears without its glyph and its words. And .statusAttention is reserved for things needing a decision — a network failure is not attention-worthy in this sense, it is a retry.

The set lives in the shared package from 5e, not the app target, or the widget's green drifts from the app's within two releases.

Where these differ from system colours

Deliberately darker than .systemGreen / .systemRed for anything carrying text, so a chip label passes contrast on white. The bright system values stay for camera overlays on a dark viewfinder, where they belong. Verify each pair against WCAG AA at the size it is used — 13px chip labels are the tight case.

6c

Regular width, keyboard first

Your reframing is the right one: design for an iPad with a keyboard and the Mac follows. That changes more than proportions — it means every action needs a keyboard route, focus order must be deliberate, and the flow has to work without a single tap. A sender at a desk entering six orders from a spreadsheet is a keyboard user, and they are the heaviest user the app has.

What the Mac needs beyond this

Little, if the split view is built properly: menu-bar commands are the shortcuts above declared once, and the sidebar is already a sidebar. What doesn't come free is the camera work in 6a — on the Mac that becomes drag-and-drop of an image onto the draft, which is the same result screen with a different door.

One thing to decide early: whether multiple drafts can be open at once. On iPhone the answer is no; on the Mac users will expect several windows, and that is a model decision rather than a layout one.

6d

Dynamic Type without overrides — the honest answer

Yes, and further than I thought

ViewThatFits removes the need for the size parameter I described: give it the horizontal tariff strip first and the vertical list second, and the 3f (folded into DesignSystem.md) reflow happens with no size class checks and no font overrides. Same for a route row — one-line and two-line candidates, let it choose. That is strictly better than what I proposed, and it keeps native Dynamic Type everywhere.

The catch is that it picks the first candidate that fits — so authoring order is the design decision, and each candidate must be acceptable on its own terms rather than a degraded version of the one above it (with the minimum-candidate rule opposite as the floor).

The ladder is the candidate list

Correcting myself: candidates need not be arrangements of the same content, so dropping elements is expressible too. The small widget's ladder is just three candidates in order — full (ETA, status, route line, address), then without the address, then ETA and status alone. Same for a Live Activity against its height ceiling. So no size parameter anywhere, and native Dynamic Type throughout: 5e's five components become candidate lists rather than parameterised layouts.

Two rules that follow from how it resolves. It measures ideal size and takes the first candidate that fits, so authoring order is the priority ranking — the design work moves into deciding what survives, which is where it belongs. And if nothing fits it falls back to the last candidate, so the last one must be the irreducible minimum that cannot overflow: for us, status and ETA, no address, no route line.

The one thing it can't judge is whether a candidate is honest. A small widget that has silently dropped the destination still looks fine — hence the truncation note from the widget board: the destination is the field the widget exists to show, so if it can't fit, the recommendation is the medium size rather than a confident-looking partial answer.

On accessibility more broadly — agreed, and better done live than drawn. The useful thing I can leave for that session is the intent: the map is an accelerator and never the only route; the tariff strip is a set of choosable elements whose limits belong in the label, not the hint; confirm-pin announces the resolved address and any correction; and a required custom field announces itself at the field, so ordering never fails silently.
